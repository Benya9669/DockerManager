# 🐳 Docker Manager

Веб-панель для управления Docker Compose проектами на сервере. Почти всё делается через WebUI: проекты из git, выбор и редактирование `.env`, build/deploy, логи, терминал в контейнере, очистка образов и контейнеров, пользователи с ролями и аудит.

## Возможности

**Проекты**
- Источник: git-репозиторий (HTTPS с токеном или SSH), существующая папка на сервере или «с нуля» (шаблон compose-файла).
- Несколько compose-файлов на проект (`docker-compose.yml,docker-compose.prod.yml`).
- **Выбор активного `.env`** из найденных `.env`, `.env.*`, `*.env`, `env/*`; передаётся как `docker compose --env-file`.
- Редактор env-файлов, создание копии (например, `.env.staging` из `.env.prod`).
- Файловый менеджер проекта: просмотр, редактирование (YAML/JSON подсветка), создание, переименование, удаление.

**Compose / Build**
- Деплой одной кнопкой: `git pull → compose pull → (build --no-cache) → up -d --build --remove-orphans`.
- `up`, `build --pull` (с опцией `--no-cache`), `rebuild` (build + `--force-recreate`), `restart`, `stop`, `down`, `pull`, `config` (проверка).
- Действия по отдельному сервису: up / restart / stop / rebuild.
- Все операции выполняются как задачи с потоковым выводом в браузер, историей и отменой.

**Безопасный деплой**
- Перед деплоем — предпросмотр: какие коммиты придут, какие файлы изменятся, дифф compose-файлов, локальные изменения, проверка `compose config`.
- Снимок перед каждым деплоем: коммит, compose-файлы, активный `.env`, ID образов контейнеров.
- После `up` панель ждёт, пока контейнеры станут здоровыми и проработают стабильно (учитываются healthcheck, коды выхода, циклические рестарты). Таймаут настраивается в проекте.
- Если проверка не пройдена — автооткат к состоянию последнего успешного деплоя: `git reset --keep`, восстановление файлов, возврат предыдущих образов (re-tag), `up`. Можно отключить в настройках проекта.
- История деплоев и ручной откат к любому успешному деплою.

**Шаблоны проектов**: Nginx + статика, PostgreSQL + Redis, Node.js, Python FastAPI, WordPress + MariaDB, Uptime Kuma. Пароли в `.env` генерируются.

**Права на уровне проекта**: глобальная роль пользователя переопределяется для отдельных проектов (нет доступа / наблюдатель / оператор). Скрытые проекты не видны нигде: ни в списке, ни в задачах, ни в контейнерах.

**Мониторинг**: CPU, память и сеть по контейнерам, CPU, память и диск сервера; история (по умолчанию 24 ч), графики на странице «Система» и во вкладке «Мониторинг» проекта.

**Несколько серверов**: удалённые Docker-хосты по SSH (`ssh://user@host`, свой ключ на сервер). Проект привязывается к хосту: compose, деплой, логи, терминал, метрики и бэкапы работают на нём, а файлы и git остаются на сервере с панелью. Выбор хоста для страниц контейнеров, образов, томов и сетей — в боковом меню. Ограничение: bind-mount'ы с относительными путями на удалённом хосте указывают на его файловую систему, используйте именованные тома.

**Бэкапы**: панель (согласованная копия SQLite, ключи, логины реестров), файлы проектов, docker-тома (потоком через `docker run … tar`, работает и для удалённых хостов). Восстановление томов и файлов из интерфейса, хранение последних N архивов, полный бэкап по расписанию.

**Интерфейс**: русский и английский, тёмная и светлая тема. Поиск по логам и выгрузка лога целиком или только найденных строк.

**Git**
- Статус: ветка, коммит, отставание/опережение upstream, локальные изменения.
- Fetch, pull (`--ff-only`), смена ветки, `reset --hard` к upstream, лог коммитов.
- Вебхуки для авто-деплоя при push (GitLab Secret token, GitHub/Gitea HMAC, generic `?token=`) с фильтром по ветке.
- Токены хранятся зашифрованными и передаются через HTTP-заголовок — не попадают в `.git/config`.

**Контейнеры и ресурсы**
- Список контейнеров (все / по проекту), start/stop/restart/remove, CPU/RAM.
- Логи в реальном времени (xterm, выбор хвоста, timestamps).
- Интерактивный терминал (`docker exec`) в браузере.
- Inspect, env, mounts, сети.
- Образы (pull, удаление, фильтр «не используются / dangling»), тома, сети.

**Очистка**
- Проект: удалить остановленные контейнеры проекта и неиспользуемые образы, собранные для него.
- Система: prune контейнеров, dangling или всех неиспользуемых образов, build cache, сетей, томов, с фильтром «старше N часов»; пресеты «мягкая / глубокая / всё».
- Отображение занятого места (`docker system df`).
- Автоочистка по расписанию (`DM_AUTO_PRUNE_INTERVAL_HOURS`).

**Логи проекта**
- Общий лог всех сервисов проекта (`docker compose logs -f`) с фильтром по сервисам, хвостом и временем.

**Приватные реестры**
- Раздел «Реестры»: логины к ghcr.io, GitLab Registry, Harbor и другим (токены хранятся зашифрованными).
- Используются автоматически во всех pull, deploy и up, при Pull образов и при самообновлении.
- GHCR: логин — GitHub-аккаунт, пароль — PAT (classic) с `read:packages`.

**Версии и самообновление**
- Версия в `VERSION`, отображается внизу меню.
- «Система» → «Версия панели»: проверка последнего GitHub Release, «Что нового», кнопка «Обновить» и принудительное обновление.
- Режимы (`DM_UPDATE_MODE`): `git` — `git pull` и пересборка образа на сервере; `image` — pull готового образа из GHCR.
- Автообновление: `DM_AUTO_UPDATE=true`, интервал проверки `DM_UPDATE_CHECK_HOURS`.
- Обновление выполняет отдельный контейнер `<проект>-updater` из образа панели, потому что панель не может пересоздать сама себя изнутри. Ход обновления: `docker logs -f dockermanager-updater` (имя зависит от compose-проекта панели).

**Доступ**
- Роли: `viewer` (просмотр, логи), `operator` (деплой, build, env, файлы, git, терминал), `admin` (проекты, настройки, очистка, пользователи).
- Аудит всех действий.

## Работа с конфигурацией и сбоями

В настройках проекта администратор задаёт окружение, например `production` или `staging`. Фильтр «Требуют внимания» на странице проектов показывает недоступные хосты, проблемные сервисы и последние неудачные деплои. В истории деплоев раскрывается диагностика, записанная перед автооткатом.

В редакторе env-файлов значения изначально скрыты. Можно открыть отдельную переменную или перейти к редактированию полного текста. При сохранении панель перечисляет изменённые ключи и проверяет версию файла. Если другой оператор успел сохранить изменения, можно принять серверный вариант или продолжить со своим черновиком. Для активного env и Compose-файлов панель показывает изменения относительно последнего применения через панель. Кнопка «Проверить и применить» проверяет конфигурацию и запускает Compose Up для проекта.

В логах проекта включите время, найдите строку и нажмите «Контекст». Ссылка открывает до 30 строк с каждой стороны события у пользователей с правами на проект, пока Docker хранит этот лог.

Для уведомлений укажите в окружении панели `DM_ALERT_WEBHOOK` (HTTPS, JSON POST) или пару `DM_TELEGRAM_TOKEN` и `DM_TELEGRAM_CHAT_ID`. При настройке обоих используется webhook. Укажите `DM_PUBLIC_URL` для абсолютных ссылок, примените переменные к контейнеру панели и включите уведомления в настройках нужных проектов. Проверка выполняется каждые 30 секунд. Три последовательных проверки unhealthy/restarting открывают инцидент. Когда все экземпляры сервиса снова работают, панель отправляет сообщение о восстановлении с длительностью сбоя.

## Быстрый старт (сервер)

```bash
git clone git@github.com:Benya9669/DockerManager.git /opt/dockermanager/app
cd /opt/dockermanager/app
cp .env.example .env        # задайте DM_ADMIN_PASSWORD, DM_PUBLIC_URL
mkdir -p /opt/dockermanager/projects ssh
docker compose up -d --build
```

Откройте `http://server:8000`. Если `DM_ADMIN_PASSWORD` не задан, пароль администратора выводится в лог (`docker logs dockermanager`) и сохраняется в `/data/initial_admin_password.txt`.

> **Важно про пути.** `DM_PROJECTS_DIR` монтируется в контейнер по *тому же* пути, что и на хосте. Иначе относительные bind-mount'ы в проектах (`./data:/data`) будут указывать в никуда: compose запускается внутри панели, но тома создаёт Docker-демон хоста. То же относится к проектам типа «папка на сервере» — их путь должен быть смонтирован одинаково.

**Уже запущенные compose-стеки:** «Проекты» → «Импорт запущенных стеков». Панель найдёт стеки по меткам контейнеров (`com.docker.compose.project`, `working_dir`, `config_files`, `environment_file`) и добавит их с тем же именем проекта, папкой, compose-файлами и env-файлом, так что дубликатов не будет. Контейнеры при импорте не перезапускаются, git-репозиторий в папке определяется автоматически. Если панель работает в контейнере, папки этих стеков нужно смонтировать по тому же пути, например `- /opt/apps:/opt/apps` в `docker-compose.yml`.

**SSH-репозитории:** укажите в `.env` папку с ключами, например `DM_SSH_DIR=/home/strgadmin/.ssh`. Она монтируется только для чтения и при старте копируется в `/root/.ssh` с правильными владельцем и правами, поэтому ваш `config` с алиасами хостов тоже работает. Если ключей несколько (`id_rsa`, `id_rsa_bny`…), в настройках проекта выберите нужный: git будет использовать только его (`-i … -o IdentitiesOnly=yes`). Там же можно скопировать публичный ключ, чтобы добавить его в deploy keys. Для HTTPS достаточно токена в настройках проекта (GitLab: пользователь `oauth2`, GitHub: любой, например `x-access-token`).

## CI/CD и релизы

GitHub Actions (`.github/workflows/ci.yml`):
- на каждый push и PR запускаются тесты бэкенда (pytest), проверка типов и сборка фронтенда;
- при push в `main` образ публикуется в `ghcr.io/benya9669/dockermanager` с тегами `edge` и `sha-xxxxxxx`;
- если версия в `VERSION` ещё не выпущена, дополнительно публикуются теги `X.Y.Z`, `X.Y`, `latest`, создаётся git-тег `vX.Y.Z` и GitHub Release с автоматическими release notes.

**Выпустить версию:** поменяйте `VERSION` (например, `0.3.0`) и запушьте в `main`. Панели на серверах увидят новый релиз.

**Приватный репозиторий:**
- Проверке обновлений нужен токен: `DM_UPDATE_GITHUB_TOKEN` (fine-grained PAT с доступом на чтение Contents этого репозитория).
- Для режима `image` добавьте `ghcr.io` в разделе «Реестры» (PAT с `read:packages`).
- Для режима `git` ключ из `DM_SSH_DIR` должен иметь доступ к репозиторию; конкретный файл ключа можно указать в `DM_UPDATE_SSH_KEY`.

## Разработка

```bash
# backend
cd backend
python -m venv .venv && .venv/bin/pip install -r requirements.txt   # Windows: .venv\Scripts\pip
.venv/bin/uvicorn app.main:app --reload --port 8000

# frontend (в другом терминале), проксирует /api на :8000
cd frontend
npm install
npm run dev     # http://localhost:5173
```

## Переменные окружения

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DM_DATA_DIR` | `./data` | БД SQLite, секретный ключ |
| `DM_PROJECTS_DIR` | `$DM_DATA_DIR/projects` | Куда клонируются проекты |
| `DM_DATABASE_URL` | SQLite | например `postgresql+psycopg://user:pass@db/dm` |
| `DM_SECRET_KEY` | генерируется | подпись JWT и шифрование токенов |
| `DM_ADMIN_USERNAME` / `DM_ADMIN_PASSWORD` | `admin` / случайный | первичный администратор |
| `DM_TOKEN_TTL_MINUTES` | `720` | время жизни сессии |
| `DM_PUBLIC_URL` | — | внешний URL для отображения вебхуков |
| `DM_ALLOW_LOCAL_PATHS` | `true` | разрешить проекты из произвольных папок |
| `DM_AUTO_PRUNE_INTERVAL_HOURS` | `0` | автоочистка каждые N часов (0 — выкл.) |
| `DM_AUTO_PRUNE_OLDER_THAN_HOURS` | `72` | чистить объекты старше N часов |
| `DM_METRICS_INTERVAL` | `30` | период сбора метрик, с (0 — выкл.) |
| `DM_METRICS_RETENTION_HOURS` | `24` | сколько хранить историю метрик |
| `DM_BACKUP_DIR` | `$DM_DATA_DIR/backups` | куда складывать архивы |
| `DM_BACKUP_KEEP` | `7` | сколько последних архивов хранить на объект |
| `DM_BACKUP_INTERVAL_HOURS` | `0` | полный бэкап по расписанию (0 — выкл.) |
| `DM_BACKUP_STOP_CONTAINERS` | `false` | останавливать проекты на время бэкапа томов по расписанию |
| `DM_BACKUP_HELPER_IMAGE` | `alpine:3` | образ для архивации томов |
| `DM_MANAGE_SSH_CONFIG` | `false` (в compose — `true`) | создавать SSH-алиасы с ключами для удалённых серверов |
| `DM_UPDATE_MODE` | `git` | самообновление: `git` или `image` |
| `DM_AUTO_UPDATE` | `false` | обновляться автоматически при новом релизе |

## Безопасность

- Доступ к `docker.sock` равен root-доступу к хосту. Публикуйте панель только во внутренней сети и за reverse-proxy с HTTPS (nginx/traefik). WebSocket-соединения (`/api/.../stream`, `/logs`, `/exec`) должны проксироваться.
- Терминал в контейнерах доступен ролям `operator` и `admin`; каждое подключение пишется в аудит.
- **Оператор фактически равен root на хосте:** он может отредактировать compose-файл (`privileged`, монтирование `/`) и запустить его. Давайте эту роль только доверенным людям.
- Порт лучше привязать к localhost и открывать панель через reverse proxy: `DM_PORT=127.0.0.1:8000`.
- Встроенная защита:
  - блокировка входа после 10 неудачных попыток с IP или 20 на логин (15 минут);
  - смена пароля, роли или отключение пользователя завершает все его сессии;
  - WebSocket подключаются по одноразовым тикетам (30 секунд), токен сессии не попадает в URL и логи прокси;
  - git-токены передаются через переменные окружения, их не видно в `ps`;
  - секрет вебхука виден только админам, переменные окружения контейнеров видны с роли оператора;
  - ввод проверяется против подстановки опций в git и docker;
  - заголовки CSP, `X-Frame-Options` и `nosniff`, IP в аудите.
- Сохраните `DM_SECRET_KEY` (или `/data/secret.key`): без него сохранённые git-токены не расшифровать.

## Архитектура и расширение

```
backend/app/
  main.py         FastAPI, статика UI, инициализация, автоочистка
  jobs.py         раннер задач: шаги-команды, стриминг вывода через WebSocket, отмена
  compose.py      построение команд docker compose (actions → steps)
  git_ops.py      git: статус, ветки, clone/pull/checkout
  dockerc.py      Docker Engine API (docker SDK)
  routers/        auth+users+audit, projects (compose/git/env/files), jobs, docker, webhooks
frontend/src/     React + Vite: pages/*, XTerm (логи/терминал/задачи), Editor (CodeMirror)
```

Новое действие добавляется в `compose.action_steps` (список команд), и оно сразу получает стриминг, историю, отмену и аудит. Новый ресурс — роутер в `routers/` плюс страница в `frontend/src/pages`.
